FPGAそのUNROLL、回路が爆発します：ソフトウェアエンジニアのためのVitis HLS

JavaScriptやPythonで書いたコードは、書いた順に実行されます。

FPGAのHLS（高位合成）では、同じ感覚でCを書くと、書いた行がそのまま「回路」になります。

その差が一番はっきり出るのが、UNROLLという指示です。

コードと回路の対応を、ソフトウェアの頭のまま追えるように整理しました。

要旨

  • HLSのUNROLLは「ループを速くする指示」ではなく「回路をコピーして並べる指示」である。
  • 展開数に比例して、FF・LUT・DSPが増える。
  • 展開内で外部依存のインデックスを引くとMUXが、除算を入れると除算器が、そのまま複製されて爆発する。
  • ソフトウェア脳のままだとアンチパターンになる。回路の形を思い描いて書き換えるのがベストプラクティスになる。

1. ソフトウェア脳のままHLSを書くと何が起きるか

FPGAは、書き換え可能なデジタル回路のチップです。

HLS（High-Level Synthesis、高位合成）は、CやC++のコードから、その回路を自動生成する技術です。

Vitis HLSは、AMD（旧Xilinx）が提供するHLSツールです。

公式サイト: https://www.amd.com/en/products/software/adaptive-socs-and-fpgas/vitis/vitis-hls.html

ソフトウェアでは、コードは「CPUが1命令ずつ実行する手順書」です。

ループを回す回数が増えれば、時間が増えます。

HLSでは、コードは「どんな回路を作るかの設計図」です。

ループ本体は、デフォルトでは1つの回路を使い回して、時間をかけて繰り返し実行されます。

つまり時間と面積（回路の大きさ）を交換する設計になっています。

この交換レートを、プラグマ（#pragma HLS ...という指示行）で動かすのがHLSの本質です。

UNROLLは、時間を削って面積を払う方向に、一気に振る指示です。

2. UNROLLは「回路のコピペ」：FF・LUT・DSPが展開数に比例して増える

次のコードを考えます。

for (int i = 0; i < 8; i++) {

#pragma HLS UNROLL

y[i] = a[i] * b[i] + c[i];

}

ソフトウェア感覚では「ループを8回まとめて回す」です。

回路としては「乗算器と加算器を8組並べる」になります。

ここで登場する部品を一言で定義します。

FF（フリップフロップ）

1ビットの値を記憶する回路です。変数やパイプラインの途中結果を保持します。

LUT（ルックアップテーブル）

任意の論理演算を表現できる小さな真理値表です。足し算や比較などの汎用ロジックは、LUTの組み合わせで作られます。

DSP

乗算や積和演算に特化した専用ブロックです。数は有限で、チップごとに上限があります。

1回分の回路が必要とするFF・LUT・DSPを、展開数だけ掛けたものが総コストです。

係数を8から64に上げれば、DSPは単純計算で8倍になります。

チップのDSP上限を超えた時点で、合成はエラーになるか、別の部品で代用して遅くなります。

ソフトウェアで言えば、`for`を8本のスレッドに割り振る話に近く、しかも「スレッド数ぶんのコア」を自分で買って並べる感覚です。

3. BRAM・URAMのポート数という壁：UNROLLしても速くならない理由

演算器を8組並べても、データが8個同時に届かなければ意味がありません。

配列は、ふつうFPGA内蔵のメモリに置かれます。

BRAM

FPGA内蔵のブロックメモリです。容量は数十Kbit単位で、同時に読み書きできるポートは通常2つです。

URAM

UltraRAMと呼ばれる、より大容量のメモリです。BRAMと同様にポート数が少なく、同時アクセスに制約があります。

8並列でa[i]を読みたいのに、ポートが2つしかなければ、1サイクルに読めるのは2個までです。

その結果、ツールは読み出しを複数サイクルに分け、UNROLLしたのに速度が出ない状態になります。

ソフトウェアで言えば、8本のスレッドが1つの共有変数をロックして取り合っている状態に近いです。

演算器の数と、メモリのポート数は別々に決まります。

UNROLLだけでなく、配列をどう配置するかをセットで考える必要があります。

4. アンチパターン①：外部依存のインデックスをUNROLL内のforで参照するとMUXが爆発する

ここから、もう一段難しい話に入ります。

MUX（マルチプレクサ）

複数の入力から1つを選んで出力する回路です。ソフトウェアの`switch`や配列の添字アクセスに対応します。

次のコードは、ソフトウェアでは自然な書き方です。

for (int i = 0; i < 8; i++) {

#pragma HLS UNROLL

y[i] = table[idx[i]];

}

idxは関数の引数など、実行時に決まる値です。

tableが分割されていない大きな配列だと、idx[i]がどの要素を指すかは、回路には事前にわかりません。

そのため、各iの読み出しごとに「全要素から1つを選ぶ」MUXが必要になります。

要素数をN、展開数を8とすると、N対1のMUXが8個できます。

Nが大きいほど、MUXは巨大になります。

また、配列を分割してレジスタに展開した場合、MUXの入力が全要素に広がるため、配線も混雑します。

これが「外部依存のインデックスで参照するとMUXが爆発する」の中身です。

ソフトウェアでは、添字アクセスはほぼ定数コストです。

回路では、添字が実行時に決まる場合、選択回路をまるごと作る必要があります。

回避策は大きく2つあります。

1つ目は、インデックスの範囲を回路側で絞ることです。たとえばアクセスを`i`に由来する定数オフセットだけに限定すれば、MUXは不要になります。

2つ目は、ARRAY_PARTITIONで配列を分割し、各iが専用のメモリだけを読むようにデータ配置を設計し直すことです。

5. アンチパターン②：UNROLL内の除算・剰余が巨大な除算器を複製する

除算も、ソフトウェアでは足し算とほぼ同じ感覚で書けます。

回路では、除算は乗算より大きく、遅い演算です。

整数の除算器は、多数のLUTとFFを使い、結果が出るまで複数サイクルかかります。

for (int i = 0; i < 8; i++) {

#pragma HLS UNROLL

y[i] = x[i] / d;

}

dが変数なら、この8行は8個の除算器になります。

1個でも重い除算器が、そのまま8個複製されます。

回路が大きくなるだけでなく、除算器の遅延が長いと、動作クロックの上限まで下がることがあります。

dが2のべき乗の定数なら、除算は右シフトになり、ほぼ配線だけで済みます。

剰余も同様で、2のべき乗ならビットマスク（`x & (d - 1)`）に置き換えられます。

定数で割る場合は、ツールが乗算とシフトの組み合わせに置き換えてくれることもあります。

ただし、それはdがコンパイル時に確定している場合の話です。

ソフトウェアでは「割り算は少し遅い」程度の認識で済みます。

HLSでは「割り算1個が、そのままチップ面積の何%か」という見積もりが要ります。

6. アンチパターンとベストプラクティスの比較

ここまでの内容を、書き方の対比で整理します。

ベストプラクティスの共通点は、「展開する前に、複製されるものが何かを数える」ことです。

複製されるのが演算器なら、DSPの数を数えます。

複製されるのがMUXなら、入力数を数えます。

複製されるのが除算器なら、定数化やシフト化で消せないかを先に考えます。

また、UNROLLだけに頼らず、PIPELINEとの使い分けも重要です。

PIPELINEは、ループ本体を段階（ステージ）に分け、前の反復の後半と次の反復の前半を重ねて実行する指示です。

回路をコピーせず、1つの回路を使い回したまま、スループットを上げます。

面積の増加が緩やかな分、まずPIPELINEで必要な速度が出るかを確認し、足りない分だけ部分展開（`factor`を指定）で補う順序が堅実です。

7. 回路をイメージしながら書くためのチェックリスト

UNROLLを書く前に、次の5点を確認します。

  • 展開数をNとしたとき、複製される演算器（DSP・LUT）はN倍になってよいか。
  • 展開内で読む配列は、同時アクセス数に見合うポート数があるか（BRAM・URAMは通常2ポート）。
  • 配列の添字は、定数オフセットか、それとも実行時に決まる値か。後者ならMUXが入る。
  • 除算・剰余は、定数またはシフト・マスクに置き換えられないか。
  • PIPELINEだけで目標の速度に届かないのか。届かないなら、部分展開で足りるか。

ツールが出す合成レポートで、LUT・FF・DSP・BRAMの使用量を見る習慣をつけると、回路のイメージが少しずつ育ちます。

読んだ回路の大きさと、頭の中の想像がずれていたら、そこがソフトウェア脳のクセが出ている箇所です。

ソフトウェアのループは、回すたびに時間を払います。

HLSのUNROLLは、回す前に面積を払います。

その払い先を、回路の形で思い描けるようになれば、「速くなるはずなのに爆発する」という失敗はずいぶん減ります。

まずは小さな係数から展開して、合成レポートの数字を眺めるところから試してみてください。
