今こそ知りたいPHP

PHPと聞くと、古い言語という印象を持つ人がいるかもしれません。

けれども、いまサーバー側の言語が分かるWebサイトの多くはPHPで動いています。

なぜ、速さや新しさだけが理由ではない言語が、これほど長く使われているのか。

その答えは、PHPの「置き方」と、置かれたまま動き続けるサイトの保守にあります。

要旨

  • PHPは、サーバー側の言語が分かるWebサイトの69.2%で使われている（W3Techs、2026年10月25日）。「終わった言語」という印象とは違う。
  • 支持されている理由は性能や新しさだけではなく、HTMLに埋め込めて、PHPとMySQLが動くサーバーなら置いて動かせる配布の形にある。WordPressは全Webサイトの39.6%を占める。
  • 一方で、PHP利用サイトの少なくとも34.6%は7系以下で、7系はすべて公式のサポートが終了済み。8.2も2026年12月31日でセキュリティ支援が終わる。
  • これからPHPを学ぶ意味は、文法の暗記ではなく、動き続けるサイトのバージョンと依存関係を保守する力を身につけることにある。

1. PHPは「終わった言語」なのか、サーバー側言語の69.2%という数字から始める

W3Techsは2026年10月25日時点で、PHPがサーバー側プログラミング言語の69.2%で使われていると公表しています。

この調査の分母は、サーバー側の言語が判別できたWebサイトです。

すべてのWebサイトの69.2%ではありません。

1つのサイトが複数の言語を使うこともあるため、合計は100%になりません。

それでも、2位のJavaScriptは8.2%、3位のRubyは7.1%です。

PHPは2位以下を大きく離しています。

W3Techsは2026年7月27日の「今日のWeb技術」で、JavaScriptがRubyを抜いてサーバー側言語の2位になったと書いています。

そのJavaScriptでも8.2%です。

数字だけを見れば、PHPは終わっていません。

ただし、使われているサイトが多いことと、新しく選ばれていることは別です。

古いサイトが動き続けているだけで数字が大きい、という可能性も残ります。

では、なぜ古いサイトは動き続けられるのか。

そこにPHPの性質があります。

2. なぜ今も使われるのか、性能ではなく「置けば動く」配布の強さ（レンタルサーバーとWordPress、全サイトの39.6%がWordPress）

PHPの公式FAQは、PHPを「HTMLに埋め込まれたスクリプト言語」と説明しています。

目標は、Web開発者が動的に生成されるページを素早く書けるようにすることです。

HTMLの中にPHPのコードを書き、Webサーバーがそれを実行してページを返します。

この形は、アプリケーションをビルドして専用の実行環境に配布するのではなく、サーバー上のファイルをそのまま実行する形に近いものです。

だから、PHPとMySQLが動くサーバーさえあれば、サイトを置けます。

WordPressの要件ページは、推奨環境としてPHP 8.3以上、MariaDB 10.11以上またはMySQL 8.0以上、HTTPS対応を挙げています。

そのうえで、PHPとMySQLをサポートするサーバーなら何でもよい、と書いています。

any server that supports PHP and MySQL will do

--- WordPress.org「Requirements」より

ApacheやNginxは推奨されていますが、必須ではありません。

この要件の緩さが、PHPの配布の強さです。

WordPressは全Webサイトの39.6%で使われ、CMS（ブラウザから記事を編集できるようにするソフト）の中では58.3%のシェアを持っています。

WordPressを動かすにはPHPが要ります。

世界で最も多く使われているCMSの土台がPHPであることは、PHPの利用規模の大きさと重なります。

性能だけが理由ではありません。

PHP 8.5の発表文は「Smarter, Faster, Built for Tomorrow」を掲げており、速度の改善が続いていることは確かです。

それでも、69.2%という規模を説明するのは、速度の比較ではありません。

同じことが、裏返しの弱点にもなります。

置けば動くということは、置いたままでも動いてしまうということです。

サイトは、誰かが止めるまで動き続けます。

PHPのバージョンが古くなっても、サイトが自動で止まるわけではありません。

3. 数字で見る現在地、PHP利用サイトのうち8系が65.5%、7系以下が34.6%という現実

W3TechsのPHPページは、PHPを使うサイトの内訳をメジャーバージョン別に出しています。

2026年10月25日時点で、8系が65.5%、7系が26.8%、5系が7.7%、4系が0.1%です。

7系以下を足すと34.6%になります。四捨五入のため、4つの合計は100.1%になります。

この内訳はサイト数をもとにした割合で、閲覧数や取引額の割合ではありません。

PHP 7.4は2022年11月28日にサポートを終え、7.3は2021年12月6日、7.2は2020年11月30日に終わっています。

5系もすべて終了しており、5.6は2018年12月31日が最後です。

つまり、少なくとも34.6%のサイトは、公式のサポートが切れたPHPで動いている計算になります。

8系が65.5%あるからといって、安心はできません。

8系の中には、2023年11月26日に終了した8.0と、2025年12月31日に終了した8.1も含まれます。

W3Techsの内訳はメジャーバージョンまでなので、8.0と8.1が何%を占めるかは分かりません。

分かるのは、セキュリティ支援を受けられないサイトが34.6%より多い可能性がある、ということです。

現在もセキュリティ支援を受けられるのは、8.2以降です。

ただし、8.2も2026年12月31日でセキュリティ支援が終わります。

積極的な支援は2024年12月31日に終わっており、いまは重要なセキュリティ修正だけが提供される期間です。

PHP利用サイトの3分の1規模が古い版に残っている、という現実は、数字の上ではっきりしています。

4. サポート期限を過ぎると何が起きるのか、パッチが当てられないサイトの構造（2年＋2年のサポート方針、8.2は2026年12月31日でセキュリティ支援終了、7.4は2022年、8.1は2025年に終了）

PHPのサポート方針は、各リリース系列が最初の安定版を出してから2年間、バグとセキュリティの問題を通常のポイントリリースで直すというものです。

その後の2年間は、重要なセキュリティ問題だけを、必要に応じて直します。

合計4年で公式のサポートが終わり、その後はEOL（サポート終了）です。

EOLを過ぎた系列について、php.netはアップグレードを強く勧めています。

If you are using these releases, you are strongly urged to upgrade

--- php.net「Unsupported Branches」より

理由も同じページに書かれています。

古い版を使うと、新しい版で直されたセキュリティ脆弱性やバグにさらされる可能性がある、というのです。

このとき効いてくるのが、PHPが「置けば動く」言語だという性質です。

サイトは、PHP本体の更新をしなくても動き続けます。

WordPressも、古い環境向けにPHP 7.4以上で動くと案内しています。

ただし、7.4系はすでにEOLで、セキュリティ脆弱性にさらされる可能性がある、と注意しています。

つまり、CMSが動くからといって、土台のPHPが守られているわけではありません。

PHP本体に脆弱性が見つかったとき、WordPressやプラグインを最新にしても、土台の修正は届きません。

サーバー会社が新しいPHPを用意していなければ、サイトの持ち主がサーバーを移すか、PHPの実行環境を変える必要があります。

動いていることに気付きにくいと、更新の順番は後回しになりがちです。

サポート期限は、サイトが止まる日ではありません。

静かに、修正が届かなくなる日です。

5. エンジニア向け、8.2から8.5へ上げる前に確認する移行の勘所（非推奨機能、拡張モジュール、CMSとフレームワークの要求バージョン、検証手順）

ここからは、PHP 8.2のサイトを8.5へ上げる作業を任されている人向けです。

8.2から8.5へは、8.3、8.4、8.5という3つのマイナーバージョンをまたぎます。

セキュリティ支援は、8.3が2027年12月31日、8.4が2028年12月31日、8.5が2029年12月31日まで続きます。

一度に飛ばさず、確認する順番を決めてから上げます。

非推奨機能：最初に見るのは、いまのコードが警告を出していないかです。

PHP 8.3では、数値でない文字列に対するインクリメントとデクリメントが非推奨になりました。

引数なしのget_class()とget_parent_class()も非推奨です。

PHP 8.4では、型の後にnullを既定値に置く「暗黙的にnullを受け入れる」書き方が非推奨になりました。

「T1 $a = null」は「?T1 $a = null」か「T1|null $a = null」に直します。

必須の引数の前に、既定値を持つ引数を置く書き方も非推奨です。

trigger_error()にE_USER_ERRORを渡す使い方、E_STRICT定数、クラス名を_だけにする書き方も非推奨になりました。

PHP 8.5では、(boolean)、(integer)、(double)、(binary)というキャスト名が非推奨です。

(bool)、(int)、(float)、(string)に置き換えます。

バッククォート演算子、セミコロンで終わるcase文、nullを配列のオフセットに使う書き方も非推奨です。

__sleep()と__wakeup()は軟非推奨（警告は出ないが、使わないほうがよい状態）になり、__serialize()と__unserialize()が推奨されています。

非推奨は、すぐに動かなくなるという意味ではありません。

警告のまま動くものもあります。

それでも、将来の版で削除される可能性を考えれば、警告をゼロに近づけておくほうが安全です。

拡張モジュール：次に見るのは、PHP本体ではなく拡張モジュールの変更です。

PHP 8.4では、DBA、ODBC、SOAPの一部がリソースからオブジェクトに変わりました。

DBAの関数はDbaのConnectionオブジェクトを、ODBCはOdbcのResultとConnectionを返すようになります。

SOAPのSoapClientのhttpurlはSoapのUrl、sdlはSoapのSdlになります。

is_resource()で判定しているコードは、falseやnullの判定に直す必要があります。

Date、Intl、PDO、Reflection、SPL、Sqlite、XMLReaderのクラス定数には型が付きました。

PHP 8.5では、IntlがICU（国際化用のライブラリ）の57.1以上を要求します。

DOMのノードリストをcloneすると失敗するようになりました。

finfo_file()は、ファイル名にnullバイトが含まれるとValueErrorを投げます。

php -mで拡張の一覧を確認し、使っている拡張が新しい版でも入るかを先に確かめます。

Composerを使っているなら、依存パッケージが要求するPHPの制約も見ます。

CMSとフレームワークの要求バージョン：PHPの対応期限より先に、CMSやフレームワークが要求を上げていることがあります。

WordPressはPHP 8.3以上を推奨しています。

8.2のサイトは、WordPressの推奨環境には届いていません。

Symfonyの現行版はPHP 8.4以上を要求しています。

8.2や8.3では、Symfonyの現行版を動かせません。

自分のサイトが使っているCMSやフレームワークが、どのPHPを要求しているかを先に確認します。

そのうえで、PHPの期限と、CMSの要求のどちらが先に来るかを見ます。

検証手順：最後に、上げ方そのものです。

本番をいきなり8.5にしないで、同じ構成のステージング環境を用意します。

8.2から8.3、8.3から8.4、8.4から8.5と、1つずつ上げます。

各段階でphp -lによる構文チェック、php -mによる拡張の確認、Composerのプラットフォーム要件チェックを行います。

テストはerror_reportingをE_ALLにして走らせ、E_DEPRECATEDのログを拾います。

決済、メール送信、ファイルアップロード、外部API連携など、拡張モジュールに依存する機能は個別に動かします。

切り戻せるように、旧バージョンの実行環境と手順を残しておきます。

ここまでやって、初めてバージョンアップは完了です。

6. 今こそ知りたいPHP、「書ける」より「保守できる」を学びの基準に

PHPの文法は、覚えようとすれば短時間で覚えられます。

PHPの開始タグと終了タグの間にコードを書き、変数と配列と関数を使えば、簡単な掲示板や問い合わせフォームは作れます。

だから、PHPは「書ける」ようになるまでの敷居が低い言語です。

しかし、サイトを長く動かす仕事は、書けることだけでは足りません。

いま動いているPHPのバージョンを知ること。

サポートがいつ終わるかを確認すること。

使っている拡張モジュールと、CMSやフレームワークの要求バージョンを把握すること。

上げる前に、どこで何が壊れるかを確かめること。

動き続けるサイトを、止めずに更新する段取りを組むこと。

これが、これからPHPを学ぶ人の基準になります。

初学者は、小さなサイトを1つ作って公開してみるとよいでしょう。

公開したら、借りたサーバーの管理画面でPHPのバージョンを確認します。

php.netのサポート一覧を眺め、自分の版がいつまで支えられるのかを見ます。

自分のサイトがどのバージョンで動いているかを知るだけで、見え方が変わります。

エンジニアは、コードを書く力に加えて、実行環境を保守する力を身につけます。

PHP本体、拡張モジュール、CMS、フレームワーク、サーバーの層を分けて考えると、何をいつ上げるかが整理できます。

PHPが長く使われてきたのは、速さの勝負だけで説明できることではありません。

置けば動くという配布の形が、Webでサイトを配る形に合っていたからです。

その同じ形が、置いたままでも動くサイトを生みました。

これからPHPを学ぶなら、文法を暗記するより先に、動き続けるサイトをどう保守するかを考えてみてください。

それが、PHPという言語の性格をいちばんよく表しています。
